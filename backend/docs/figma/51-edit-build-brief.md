# Edit product flow: decisions and build brief

Study: `50-edit-product-flow-analysis.md` (7 screens). Shared rules: `20-build-brief.md` (ownership, conventions, tests, report) and `41-creation-build-brief.md` section 0 (tooling traps: never write `\uXXXX` escapes through tools, no shell heredocs with quotes, no git, run only your own tests with `--maxWorkers=1`, typecheck only your module).
This file: decisions, the contract between the three work packages, the API per package.

## 1. Decisions (what large commerce platforms do, and what we do)
| # | Question | Market practice | Decision |
|---|---|---|---|
| E1 | Master code after listing | Amazon / Flipkart: a seller SKU cannot be changed once listed; Shopify allows edits | **Locked once the product is not a draft**: `PATCH /products/{id}` and the edit save answer 409 `code_locked` (rule in `error.details.rule`) when the code would change; drafts stay editable. DTO flag `productCodeLocked`. |
| E2 | Which edits need confirmation | Listing-affecting structural changes (category, type) warn first | **Category change and product-type change require confirmation** (`confirm: true`); name, description, brand, attributes do not. |
| E3 | Do edits reach live listings | Shopify / PIMs push master content; marketplaces cap what can change | **Inherited master content is pushed to live listings automatically when the connector supports `listings.update`**; otherwise the listing becomes `needs_republish` and shows up in Needs attention. Fields a channel overrides in `product_marketplace_data` are **never overwritten** (the channel is "independent" for that field). Listings that are not live (draft / ready / approved) are not touched: the existing approval hash already forces re-approval before publishing. |
| E4 | Which channels are independent | Channel-specific content wins | A listing is independent for field F when `product_marketplace_data(productId, marketplace).data` has a non-empty override for F (keys: `title`, `description`, `brand`, `bullets` count as description, `attributes.*`: the LISTINGS package reads how the listing input builder uses these keys and documents the mapping). |
| E5 | Category change on live listings | Marketplaces restrict category changes of live listings (re-listing may lose reviews) | **Never auto-remapped.** Every live listing of the product goes to `content_state = needs_review` with `content_review = { reason: 'category_changed', fromCategoryId, toCategoryId, suggestedMarketplaceCategoryId, suggestedMarketplaceCategoryName }` (the suggestion comes from `category_mappings` for the new category when one exists). The seller resolves it per listing (accept the mapping, keep the current marketplace category, or choose another). |
| E6 | "Description shorter than the category average" | Listing-quality tools compare against peers | Benchmark = **median plain-text description length of the business's other active products in the same category (needs >= 5 such products)**, else a **150-character floor**; the insight shows when the description is shorter than the benchmark and not dismissed. |
| E7 | AI Apply in the editor | Suggest, preview, approve; the page's Save is the commit | `apply` gets `persist: false`: the suggestion is accepted (decision recorded) but the product is **not** written; the editor holds the text until Save. `persist: true` (default) keeps today's behaviour. |
| E8 | "Confirm factual and tax details" | Facts are the seller's responsibility | Material, dimensions, weight, country, HSN, tax are plain editable facts (no extra confirmation flag); only supplied values are inherited by listings; custom attributes keep their `confirmed` flag (unconfirmed ones are never inherited). |
| E9 | "N attributes configured" | counter of filled attributes | Real count: supplied slots among {material, dimensions, weight, country of origin, HSN code, tax information} + confirmed custom attributes. The design's "6" with nothing supplied is mock data. |
| E10 | Readiness percent | consistent across screens | **The edit panel percent equals the content-readiness percent of `GET /products/{id}/content`** (same product, same number everywhere); the panel groups the same checks into four items. |
| E11 | Other editor tabs | | Media, Details, Variants, Inventory, Listings, Content, Activity reuse the existing detail endpoints (no new edit endpoints). |

## 2. Contract between the packages (exact names)
### LISTINGS exports (`modules/listings/src/index.ts`, `@oms/mod-listings`)
```ts
export type ContentField = 'title' | 'description' | 'brand' | 'category' | 'productType' | 'material' | 'dimensions' | 'weight' | 'countryOfOrigin' | 'hsnCode' | 'gstRate' | 'customAttributes' | 'tags';
export interface ProductChange { fields: ContentField[]; category?: { fromId: string | null; toId: string | null } }
export interface ListingImpact {
  listingId: string; variantId: string; sku: string; accountId: string; accountName: string; marketplace: string; marketplaceName: string;
  listingStatus: string; live: boolean; supportsUpdate: boolean;
  independentFields: ContentField[];            // channel overrides (never overwritten)
  inheritedFields: ContentField[];              // changed fields this listing inherits
  effect: 'inherited' | 'independent' | 'may_need_remapping' | 'not_live' | 'unaffected';
  mappingState?: 'mapped' | 'needs_review';     // only for category changes
  suggestedMarketplaceCategoryId?: string | null; suggestedMarketplaceCategoryName?: string | null;
}
/** read-only preview used by change-impact */
export function previewProductChange(tx: Tx, vendorId: string, productId: string, change: ProductChange): Promise<ListingImpact[]>;
/** marks the listings in the CALLER's transaction (content_state / content_changed_fields / content_review) and returns the plan; call requestContentSync after commit */
export function applyProductChange(tx: Tx, vendorId: string, productId: string, change: ProductChange): Promise<{
  listings: Array<{ listingId: string; accountId: string; marketplace: string; marketplaceName: string; state: 'sync_pending' | 'needs_review' | 'needs_republish' | 'independent' | 'unchanged' | 'not_live' }>;
  accountsToSync: string[];
}>;
/** after commit: one coalesced content-sync job per account (idempotent) */
export function requestContentSync(c: Container, vendorId: string, accountId: string, trigger?: 'event' | 'manual'): Promise<unknown>;
/** counts for the readiness panel: listings of the product by content_state / status needing attention */
export function productListingContentSummary(tx: Tx, vendorId: string, productId: string): Promise<{ total: number; needsReview: number; syncPending: number; failed: number; needsRepublish: number; rejected: number }>;
```
Schema (already migrated, frozen): `marketplace_listings.content_state ('synced'|'sync_pending'|'needs_review'|'needs_republish'|'failed')`, `content_hash`, `content_changed_at`, `content_synced_at`, `content_error`, `content_changed_fields (jsonb string[])`, `content_review (jsonb)`; `product_insight_dismissals`.

### EDIT -> CATALOG (additive, owner: the EDIT package edits these catalog files only: `service.ts`, `routes.ts`, `schemas.ts`, `creation.ts` where needed)
* Master code lock rule (E1) in the shared update path (`updateProduct` / `applyProductPatch`): applies to `PATCH /products/{id}`, `edit/save`, bulk update paths and imports (CSV import that tries to change a code of a non-draft product is a row error). Drafts and `POST /products/{id}/draft` are exempt. `productCodeLocked` added to the product DTO.
* Do NOT touch `ai-description*.ts` (AI package) or `description.ts` semantics.

## 3. API to build
### Package EDIT (owner `modules/product-edit/**` + the catalog files above; tests `tests/api/product-edit.test.ts`, `tests/api/product-edit-walkthrough.test.ts`)
1. `GET /products/{id}/edit` (`products:read`) -> `{ product: editor DTO (same as the creation DTO's product plus productCodeLocked), version, status, locks: { productCode: { locked, reason } }, meta: { productId (= master code), createdAt, updatedAt, updatedBy: { id, name } | null }, nav: [{ key: overview|media|details|variants|inventory|listings|content|activity, label, count? }], attributes: { configured, slots: [{ key: material|dimensions|weight|countryOfOrigin|hsnCode|taxInformation, supplied }], note }, media: { primaryImageUrl, thumbnails (max 3), total }, inheritance: { channels: [{ code, name, accountId, listingId, listingStatus, independentFields }], text }, readiness: { percent, items: [{ key: core_information|product_media|required_attributes|marketplace_content, label, state: done|pending, detail?, action? { label, href } }] }, insights: [ ... ] }`. `attributes.note` = "Attribute values were not supplied in the existing product record. Confirm factual and tax details before distributing them." only when some slot is unsupplied. Readiness percent = the content-readiness percent of the product (reuse the same function as `GET /products/{id}/content`; do not recompute differently); `marketplace_content` item: open when any listing has `needs_review`, `needs_republish`, `failed` or status rejected / correction_required, detail "N marketplace listing(s) need(s) content review." and action Review -> listings of the product.
2. `POST /products/{id}/change-impact { changes: {...editor fields...} }` (`products:read`) -> `{ hasChanges, items: [{ field, label, message }], summary ("Product name changed" / "Category changed" / "N fields changed"), listings: { potential, live }, channels: [{ code, name, accountId, listingId, effect: name_inherited|description_inherited|brand_inherited|attribute_inherited|type_inherited|may_need_remapping|independent|not_live|unaffected, independentFields, supportsUpdate, mappingState?, suggested?: {...} }], independentNote ("<Channel> content is independently managed."), notSentNote ("Updates are not sent to listings until you save."), requiresConfirmation, confirmation?: { title: "This change may affect connected listings.", message: "N marketplace listings may need to be remapped.", mapping?: { from: categoryName, to: categoryName }, channels: [{ code, action: 'category_mapping_review' }] } }`. No writes. `changes` identical in shape to the editable fields; unchanged values (equal to the baseline) are ignored; an empty/no-op change returns `hasChanges: false` ("No changes yet").
3. `POST /products/{id}/edit/save { version, changes, confirm? }` (`products:write`): validates with the strict field rules of the creation flow (+ active-product rules: title >= 3, category cannot be cleared, an active product keeps >= 1 active variant, code locked), requires `confirm: true` when the impact says `requiresConfirmation` (else 409 `CONFLICT` with `details.rule = 'confirmation_required'` and `details.impact`), then in ONE transaction: patch the product (reuse the catalog patch path), `applyProductChange`, write audit `product.edited` with per-field before/after and the listing plan, emit `product.updated` (+ `product.edited`); after commit call `requestContentSync` for each account to sync. Response: `{ saved: true, noChanges: false, savedAt, version, product, impact: { listingsQueued, channels: [{ code, name, listingId, state: sync_pending|needs_review|needs_republish|independent|unchanged|not_live }], text: "3 listings will sync shortly." , notSyncedYet: "Saved to the master product. Listings have not synced yet." }, readiness, insights }`. A save with no effective change answers 200 `{ saved: false, noChanges: true }` and writes nothing. Stale `version` -> 409 `VERSION_CONFLICT` with `details: { currentVersion, current: editor DTO, updatedAt, updatedBy }` so the UI can offer reload/merge. Idempotent with the `Idempotency-Key` header.
4. Insights: `GET /products/{id}/insights` (all current, not dismissed), `POST /products/{id}/insights/{key}/dismiss { until? }`, `POST /products/{id}/insights/{key}/restore`. Keys: `description_short` (E6; message "Your product description is shorter than the average for this category.", detail "Adding key product benefits may improve listing completeness.", actions Review suggestion -> the AI description endpoint with mode `benefits` and Dismiss) and `few_images` (fewer than 3 real images (placeholders do not count): "Add more product images", detail "Listings with several images convert better.", action Manage media). Dismissals live in `product_insight_dismissals`; dismissals are per product and per key; an insight whose condition no longer holds disappears on its own.
5. Master-code lock (see section 2) with tests, including that drafts remain editable and the CSV import row error.
6. Tests: the 7 screens as a walkthrough (like `tests/api/product-creation-walkthrough.test.ts`: real sandbox marketplaces (mock, amazon_in, flipkart, myntra) with live listings, name change -> impact "name_inherited" for channels and "independent" for one channel with an override in `product_marketplace_data`; unchanged state; category change -> `requiresConfirmation` and the confirmation payload; save with `confirm` -> channels `sync_pending` / `needs_review`; AI preview unaffected; additional attributes counts; unsaved navigation = no server state (a second `GET /edit` shows the unchanged product)); plus unit-style tests for every rule (field-level validation, version conflicts, idempotency, lock, noop, permissions: viewer cannot save/dismiss but can read, staff can edit, tenant isolation, concurrency: two saves with the same version -> one success).

### Package LISTINGS (owner `modules/listings/**`; also `modules/issues/src/detectors.ts` for two detectors; tests `tests/api/listing-content-sync.test.ts`)
1. Implement the exports of section 2 with the exact signatures. Content that listings inherit = the master fields in `ContentField`; define `contentHash(productFields, overrides)` per listing (stable, excludes fields the channel overrides) and keep it in `content_hash`.
2. Consumer for `product.updated` (fallback for edits coming from any route: plain PATCH, CSV import, AI apply): map `payload.fields` to `ContentField`s (when the payload has no fields, compare the content hash) and call the same marking logic idempotently (no double marking when `edit/save` already marked the same change: compare `content_hash`).
3. Content sync job: handler named `listings.content-sync` (queue `syncMarketplace`, one coalesced job per account via the sync engine; idempotent; honours the ConnectorHost rate limiter, retries with backoff, dead-letters like other sync jobs): for each listing in `sync_pending` of the account build the listing input from the **current master content** (existing builder, channel overrides win), call `connector.updateListing` only when the capability `listings.update` is enabled; success -> `synced` + `content_hash` + `content_synced_at`; failure -> `failed` + `content_error` (retryable); connectors without the capability -> `needs_republish` (set by `applyProductChange` already). Update the sandbox connectors that declare `listings.update` so the flow works end to end in tests, with a failure-injection hook in `mockControl`-style helpers (look at `packages/testing` and `packages/connectors`; those packages are not yours: if you need a test hook there, build it inside your test file with the existing control objects, and list the need in the report).
4. Endpoints (all `/api/v1`): extend `GET /listings` with `filter[contentState]`, `filter[productId]` (if missing) and DTO fields `contentState`, `contentChangedFields`, `contentReview`, `contentError`, `contentSyncedAt`; `POST /listings/{id}/content-sync` (listings:write; retry for `failed`, force for `sync_pending`; 409 when `needs_review` or not live), `POST /listings/{id}/content-review/resolve { action: 'accept_mapping' | 'keep_current' | 'set_category', marketplaceCategoryId? }` (accept: sets `marketplace_category_id` from the suggestion, `sync_pending`; keep: clears the review, `synced`; set: validates the id against the marketplace category tree (existing category search) then `sync_pending`), `GET /products/{id}/listing-content` (per listing content state of a product for the "View affected listings" link; products:read + listings:read; paged is not required).
5. Issues: two detectors in `modules/issues/src/detectors.ts`: `listing_content_review` (area listings, listings in `needs_review`, priority medium, title "N listings need a category mapping review"-style wording consistent with the others) and `listing_content_failed` (area listings, `failed` or `needs_republish`, priority high, "N listings could not be updated with the latest product content"); add focused tests in your own test file (do not edit `tests/api/issues-dashboard.test.ts`).
6. Existing listing tests and e2e must stay green; the approval hash behaviour stays unchanged.

### Package AI-EDIT (owner `modules/catalog/src/ai-description*.ts` and `tests/api/product-ai-description.test.ts`)
1. `mode: 'concise'` with source text (request `text` or the saved description) now **condenses the existing text** (removes filler such as "designed for" -> "for", "in order to" -> "to", intensifiers, repeated words/clauses, trailing redundant phrases; must be shorter than the source, or `unchanged: true`; never adds a word that is not in the source or in a small closed list of function words); with no text it keeps the creation behaviour (sentence from name + category). `rewrite` also simplifies "designed for/made for/built for X" -> "for X" and inserts a comma between consecutive adjectives from a closed adjective list (durable, premium, lightweight, spacious, stylish, compact, sturdy, ...) so that "A durable premium travel bag designed for short business trips and weekend travel." becomes "A durable, premium travel bag for short business trips and weekend travel." (the design sample).
2. Responses gain `explanation` (string) and optional `alternatives: [{ mode, text, html, explanation }]` when the request has `alsoSuggest: ['concise']` (or `['rewrite']`; max 1, different mode). Explanations: for rewrite/concise on existing text: "Simplifies the sentence using only your existing description. No new features or product claims have been added. Your original remains unchanged above." (concise may say "Shortens ..." similarly: pick wording that is true for what it does); benefits/creation keep the grounding note.
3. `apply { version?, persist? = true }`: with `persist: false` the suggestion is marked applied (decision + audit `product.ai_description_accepted`), the response is `{ suggestion, text, html }` and the product is NOT written (version not required); with `persist: true` behaviour is unchanged.
4. Tests extended accordingly (exact strings for the design samples, never longer, no new words, idempotency, injection, persist false does not change `updated_at`/version). Keep all existing tests green.

## 4. Quality bar
Same as before: tenant filters + RLS, transactions, no N+1 (batched queries by listing/account), bounded work (max 500 listings per product processed per call; beyond that 413 with a clear message), idempotency, audit + outbox, route policy (tags/summary/response schemas/permissions), Swagger id collisions (never name a meta id `XInput` if `X` exists), error details in `error.details.rule`, tests with real numbers. No random behaviour: every rule above is the spec; anything you must assume goes in the report under "assumptions".
