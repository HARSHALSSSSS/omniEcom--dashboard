# Backend readiness for the frontend screens: build brief

Goal: after this work every screen of `frontend/` has a complete, production-grade backend (no missing API, no screen that has to fake data), so the next step can be integration. Study first: `docs/integration/01-frontend-analysis.md` (screen by screen gaps). The frontend code is the specification of what each screen shows: read the page (`frontend/src/pages/...`), its `types/*.ts`, `constants/*`, and the MSW data (`frontend/src/mocks/data/*`, `mocks/handlers/*`). Where the frontend invented something unreasonable (fake rating, hardcoded numbers) build the honest backend equivalent and say so in the report.

**Rule of design:** the backend contract stays the source of truth for everything that already exists (paths, envelope, `filter[x]` style, minor units, version locks). Only add what is missing: new modules, new endpoints, extra fields, composite read models that make one screen a one or two call affair. Never rename or break an existing endpoint or DTO field (other tests and the frontend adapters depend on them). New fields are additive.

## 0. Shared rules (all packages)
* Conventions of this repo: read `docs/figma/20-build-brief.md` (ownership, conventions, tests, report format) and section 0 of `docs/figma/41-creation-build-brief.md` (tooling traps) first. Reminders: never write `\uXXXX` escapes through tools (use `\x` or code points); no shell heredocs with quotes (use Write/Edit); NO git commands; never touch `C:\Users\Lenovo\field_work_cam`.
* Module architecture: `modules/<name>/src/{manifest.ts (GENERATED), http/routes..., service, schemas}`; a module may import other modules only through their `index.ts` and only modules listed in `dependsOn` of `scripts/scaffold-modules.mjs` (already declared generously; the graph is acyclic and `pnpm check:modules` must stay green). Do NOT run `scripts/scaffold-modules.mjs` and do NOT run `pnpm install` (other agents work in parallel). If you need a dependency edge that is not declared, do not invent a cycle: put the code in a module that already depends on what you need and say so in your report.
* Route policy: every route needs `config.access` (permission), tags, summary, and a 2xx response schema; OpenAPI meta ids must not end in `Input` when the base id exists. Success envelope `{ success, data, requestId }`; keyset lists add `meta { limit, nextCursor, hasMore }`; numbered lists use `data { items, page, pageSize, total, pages }`. Errors via `Errors.*` from `@oms/shared` with `details.rule` for business rules (the error code list is fixed).
* Money is integer minor units (`*_minor`), rates are basis points (`*_bps`). Tenant isolation: PostgreSQL RLS plus explicit `vendor_id` filters in every query. Writes: audit log + outbox event where the neighbouring code does it; optimistic `version` on mutable aggregates; `Idempotency-Key` support on side-effect POSTs like the neighbours. Background work goes through the existing job/queue/scheduler mechanisms (look at how `listings`, `analytics`, `pricing` register jobs and schedules); do not invent a new queue.
* Schema is FROZEN (see section 1). Do not edit `packages/database/**` and do not add migrations. If a column is missing, store the data in an existing jsonb column or report the need; do not touch the schema.
* Permissions are FROZEN in `packages/auth/src/rbac.ts` (added: `promotions:*`, `procurement:read|write|approve`, `imports:read|write`, `reports:write`, `pricing:approve`). Reuse existing ones otherwise.
* No external network and no new npm dependencies (offline install). Anything like XLSX, PDF or ZIP must be written with Node built-ins (`node:zlib`, `node:crypto`) or existing dependencies; check `node_modules` of the repo first.
* Frontend is read-only for you (do not edit `frontend/`).
* Tests: add focused API tests under `tests/api/<your-name>.test.ts` (and unit tests where logic is pure) with a walkthrough of the screen flows with the numbers and labels of the screen, plus rule tests (validation, permissions: viewer reads but cannot write, staff vs admin where relevant, tenant isolation, concurrency/version conflicts, idempotency, error cases). Run ONLY your own test files with `pnpm exec vitest run <file> --maxWorkers=1` and typecheck only your module with `pnpm exec tsc -p modules/<name>/tsconfig.json --noEmit` (or the package that you changed). Existing tests that your change legitimately breaks may be updated minimally (say which and why); never weaken a test to hide a bug.
* Keep each file readable (< ~600 lines), match the surrounding code style and comment density, no dead code, no TODO placeholders, nothing about Claude/Anthropic anywhere in code or docs.
* Final report to me (short, plain): what you built (endpoint list with method + path + permission), what you changed in files you do not own (should be near zero), deviations/assumptions, anything that could not be done and why, test files + counts.
