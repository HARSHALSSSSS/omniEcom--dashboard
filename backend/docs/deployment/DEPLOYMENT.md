# Deployment

## Artefacts

One Dockerfile (`infrastructure/docker/Dockerfile`) builds every process: `--build-arg APP=api|worker|scheduler|webhook-worker`.

- **Bundle**: `tsup` bundles our workspace packages; third-party packages stay external and are listed with **exact installed versions** in `dist/package.json` (generated by `scripts/tsup-app.mjs`). Native modules (argon2) and packages that read files at runtime (bullmq) therefore work.
- **Runtime image**: `node:22-alpine`, `npm install --omit=dev` from that file, **non-root**, `HEALTHCHECK` on `/health/live`. Verified locally by installing the generated `dist/package.json` into an empty directory and booting the bundle.
- **`migrate` target**: full workspace image that runs `db:migrate` then `db:seed` with the owner role.
- **Frontend image** (`frontend/Dockerfile`): Vite build, then `nginxinc/nginx-unprivileged` (uid 101, port 8080). See "Web app" below.
- Image tags: git SHA + semver; deploy by immutable tag.

## Release flow

```
PR → CI (.github/workflows/ci.yml): backend typecheck · lint · check:modules · tests · OpenAPI contract · build · integration (Postgres+Redis) · docker builds
                                    frontend tsc · eslint · vitest · build · npm audit (advisory) · docker build
main → deploy.yml calls CI first (workflow_call). Only if it is green: build+push images (tag = sha) for api, worker, scheduler, webhook-worker, migrate, frontend
deploy: 1) run `migrate` job (owner role)   2) roll workers + api (maxUnavailable 0)   3) smoke test (E2E_BASE_URL) 
rollback: redeploy previous image tag. Migrations are expand/contract so the previous version still works against the new schema.
```

Order matters: **migrate first, then app**; the new schema must be backward compatible with the *running* version (additive changes; destructive ones in a later release).

## Web app (frontend)

- **Image**: `frontend/Dockerfile` (multi-stage). `VITE_*` values are compiled in at build time from `frontend/.env.production` (`VITE_API_BASE_URL=/api/v1`, `VITE_USE_MOCKS=false`); they are public, never put secrets in them. Override with `--build-arg`.
- **Same-origin API**: the browser calls `/api/v1/*` on the web host. In Kubernetes the Ingress `oms-web` (host `app.<domain>`) routes `/api/v1` to `oms-api` and everything else to `oms-frontend`, so no CORS is needed. The image also proxies `/api/` itself to `API_UPSTREAM` (default `http://oms-api`), so it works standalone: `docker run -p 8080:8080 -e API_UPSTREAM=http://host.docker.internal:3000 oms-frontend`.
- **nginx** (`frontend/nginx.conf`, rendered by envsubst at start): SPA fallback to `index.html`; gzip; `/assets/*` cached for a year (`immutable`, content-hashed by Vite); `index.html` never cached; `/healthz` for probes. Security headers on every response: CSP (self + Google Fonts for `fonts.googleapis.com`/`fonts.gstatic.com`; `img-src 'self' data: blob:`; `connect-src 'self'`; `frame-ancestors 'none'`), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, COOP, HSTS. Remote (http/https) product image URLs are blocked by the CSP by design: images are served from the API as authenticated blobs. If you must allow a CDN, add its origin to `img-src` in `frontend/security-headers.conf`.
- **Pod**: non-root (101), `readOnlyRootFilesystem` with writable `emptyDir` mounts for `/tmp`, `/var/cache/nginx` and `/etc/nginx/conf.d` (where the rendered config goes), all capabilities dropped, probes on `/healthz`, PDB, 2 replicas (`infrastructure/k8s/base/frontend.yaml`).
- **Edge exposure policy**: the API ingress (`oms-api`) routes only `/api/v1/*` plus the exact paths `/health/live` and `/health/ready` (status only; dependency detail is hidden in staging and production). `/metrics`, `/docs` and `/health` are not routed; Prometheus scrapes pods directly and `/metrics` also needs `METRICS_TOKEN`.
- **Local**: `cd frontend && npm ci && npm run dev` (Vite proxies `/api` to `VITE_PROXY_TARGET`, default `http://localhost:3000`).

## Process topology and sizing (starting point)

| Process | Replicas | Scale on | Notes |
|---|---|---|---|
| api | ≥ 2 | CPU / RPS | stateless, `TRUST_PROXY=1` (hop count), PDB `minAvailable: 1`, preStop sleep for LB drain |
| worker | ≥ 2 | queue depth (KEDA) | split pools with `WORKER_QUEUES` (e.g. dedicated `marketplacePush`) |
| webhook-worker | ≥ 2 | queue depth | isolates webhook storms |
| scheduler | 1–2 | n/a | idempotent; replicas are safe |

Reference manifests: `infrastructure/k8s/base` (Deployment, Service, HPA, PDB, probes, hardened securityContext). Probes: startup/liveness `/health/live`, readiness `/health/ready`.

## Graceful shutdown

SIGTERM → stop accepting HTTP (idle connections closed) → workers finish in-flight jobs (`terminationGracePeriodSeconds: 60`) → close queues → DB pool → Redis → flush traces. Hooks run in reverse registration order, once.

## Database operations

- Run migrations with `DATABASE_MIGRATION_URL` (owner). App uses `DATABASE_URL` (`oms_app`, `NOBYPASSRLS`).
- Behind PgBouncer use **transaction pooling** (compatible with transaction-local tenant settings).
- Provision the two roles via IaC using `infrastructure/postgres/init.sql` as the reference.
- Backups: PITR + daily snapshot; restore drill quarterly.

## Secrets and config

Inject through the platform (External Secrets/CSI/Parameter Store). Required in production: `DATABASE_URL`, `DATABASE_MIGRATION_URL` (migrate job only), `REDIS_URL`, `JWT_ACCESS_SECRET`, `ENCRYPTION_KEYS`, storage settings, `PUBLIC_BASE_URL`, `CORS_ORIGINS`, `SMTP_URL`, `EMAIL_FROM`. Validation at boot rejects missing/weak values.

`NODE_ENV=production` additionally refuses to boot when (all problems are listed at once, see `packages/config/src/production.ts`):

- `SMTP_URL` is missing / not `smtp(s)://` / points at localhost, or `EMAIL_FROM` is missing, malformed or on a placeholder domain (`example.com`, `localhost`...). Without SMTP no verification, password-reset or invitation e-mail would ever be delivered.
- `REDIS_URL` is the localhost default or not `redis(s)://`.
- `STORAGE_DRIVER=s3` without `STORAGE_ENDPOINT` (not localhost), `STORAGE_BUCKET`, `STORAGE_ACCESS_KEY_ID` and `STORAGE_SECRET_ACCESS_KEY`, or with MinIO's development credentials.
- `MOCK_MARKETPLACE_ENABLED=true` or `SANDBOX_COURIER_ENABLED=true` (staging may keep them for rehearsals; staging does not enforce the SMTP/Redis/storage items above).

### E-mail

`SMTP_URL` set selects the SMTP mailer (nodemailer, pooled); unset selects the log mailer (development/test only). Examples: `smtps://apikey:SECRET@smtp.provider.com:465` or `smtp://user:pass@smtp.provider.com:587` (STARTTLS). Token mails (verify, reset, invitation) carry the link in both the plain-text and HTML body. The link is **never** logged by the SMTP mailer, and the log mailer prints links only outside production. Transient failures (timeouts, 4xx) are retried 3 times with exponential backoff inside the mailer; permanent failures (bad credentials, 5xx) are not retried. Failures are logged with a scrubbed error (code and message, credentials stripped) and never surfaced to the requester (so account existence is not leaked). Mail is sent inline after the database commit, not through a queue. Use a provider with a bounce/complaint webhook and set up SPF, DKIM and DMARC for the `EMAIL_FROM` domain.

### Error tracking

`SENTRY_DSN` set sends unexpected errors to Sentry (`@sentry/node`), in addition to the structured log line. Only the request id, route template, vendor id and queue/job id are sent as tags; request bodies, headers, cookies, users and query strings are stripped (`sendDefaultPii: false` plus a `beforeSend` scrubber). Unset keeps log-only tracking.

## Go-live checklist (needs real hosts / credentials)

- [ ] Real DNS names and TLS secrets: edit the hosts in `infrastructure/k8s/base/platform.yaml` and the overlays (`api.example.com`, `app.example.com`, and the staging patches); create `oms-api-tls` and `oms-web-tls`.
- [ ] Container registry: repository variable `REGISTRY`, secrets `REGISTRY_USER`/`REGISTRY_TOKEN` (the deploy action rewrites `registry.example.com` through the overlay `images:` mapping).
- [ ] Kubernetes secrets: `oms-secrets` (runtime role `DATABASE_URL`, `REDIS_URL`, `JWT_ACCESS_SECRET`, `ENCRYPTION_KEYS`, `METRICS_TOKEN`, storage keys, `SMTP_URL`, `SENTRY_DSN`) and `oms-migration-secrets` (owner `DATABASE_MIGRATION_URL`). Set `EMAIL_FROM` in the overlay `oms-config`.
- [ ] Postgres: roles per `infrastructure/postgres/init.sql` (owner for migrations, restricted `oms_app` for the runtime), managed instance with TLS and PITR.
- [ ] Redis with `noeviction`, a private S3 bucket with its credentials, an SMTP relay (SPF/DKIM/DMARC) and a Sentry project.
- [ ] Marketplace platform credentials (`AMAZON_IN_LWA_*`, `FLIPKART_*`, ...) when going live with those channels.
- [ ] GitHub settings: see [docs/BRANCH-PROTECTION.md](../../../docs/BRANCH-PROTECTION.md).
- [ ] Prometheus scrape of pod `/metrics` with the `METRICS_TOKEN` bearer, alerts from `infrastructure/observability/alerts.yml`.
